1. Обзор

Звонки в мессенджере используют WebRTC для передачи аудио и видео. Защита трафика достигается на двух уровнях:

  • Сигнализация — обмен SDP и ICE-кандидатами для установки соединения идёт по защищённым каналам (HTTPS, WSS).
  • Медиа-потоки — аудио и видео шифруются по умолчанию с помощью DTLS-SRTP, встроенного в WebRTC.

Браузеры требуют шифрование медиа в WebRTC: без DTLS-SRTP соединение не устанавливается. То есть голос и видео между участниками звонка передаются только в зашифрованном виде.

КомпонентПротокол/механизмЧто защищает
API и WebSocket HTTPS, WSS TLS SDP, ICE, события вызова, аутентификация
Медиа (RTP) SRTP шифрование Аудио и видео в реальном времени

2. Защита сигнализации

Сигнализация — это обмен служебной информацией: приглашение в звонок, SDP (Session Description Protocol) с кодеками и параметрами, ICE-кандидаты для установки соединения через NAT. Вся эта информация передаётся через приложение, а не напрямую между браузерами.

Каналы сигнализации

КаналПротоколИспользование
API (calls.php, WebSocket) HTTPS / WSS Конфиг, SDP offer/answer, ICE-кандидаты, события invite/accept/reject/end
SIP (опционально) WSS (SIP over WebSocket) INVITE, 200 OK, ACK — при режиме SIP

Все запросы к API и события WebSocket идут поверх TLS (HTTPS/WSS). Сервер и клиент используют сертификаты; данные в transit защищены от прослушивания и подмены (при корректной конфигурации TLS).

Важно: SDP содержит метаданные (кодеки, IP-адреса в ICE-кандидатах). Хотя они не раскрывают содержимое разговора, перехват SDP может дать информацию о сетевой топологии. Поэтому передача SDP только по WSS/HTTPS обязательна.

3. Защита медиа-потоков

Аудио и видео передаются по RTP (Real-time Transport Protocol). WebRTC использует его защищённый вариант — SRTP (Secure RTP), который обеспечивает:

  • Конфиденциальность — шифрование payload’а RTP/RTCP
  • Целостность — аутентификация сообщений (HMAC)
  • Защиту от повтора — счётчик/sequence number

Симметричные ключи SRTP

Ключи для SRTP не передаются в открытом виде. Они вырабатываются в процессе DTLS handshake между peer’ами (браузерами или браузером и TURN/медиа-сервером). Протокол DTLS-SRTP (RFC 5764) определяет, как из сессии DTLS получить мастер-ключи для SRTP.

В типичном сценарии WebRTC (p2p между двумя браузерами):

  1. Каждый peer создаёт свой сертификаат (в браузере — генерируется автоматически)
  2. Выполняется DTLS handshake для установления шифрованного канала
  3. Из DTLS-сессии экспортируются ключи SRTP
  4. Весь RTP/RTCP трафик шифруется этими ключами

4. DTLS и SRTP

4.1 DTLS (Datagram TLS)

DTLS — это адаптация TLS для UDP. В WebRTC он используется:

  • Для защиты канала DataChannel (если используется)
  • Как основа для выработки ключей SRTP (DTLS-SRTP)

Алгоритмы шифрования в DTLS определяются согласованием между браузерами. Современные браузеры поддерживают, в частности, AES-GCM, ChaCha20-Poly1305.

4.2 Ключевая схема DTLS-SRTP

Выработка ключей SRTP из DTLS
flowchart LR subgraph A[Браузер A] D1[DTLS Handshake] K1[Ключи SRTP] end subgraph B[Браузер B] D2[DTLS Handshake] K2[Ключи SRTP] end D1 <-->|UDP, зашифровано| D2 D1 --> K1 D2 --> K2 K1 --> M1[SRTP аудио/видео] K2 --> M2[SRTP аудио/видео] M1 <-->|зашифрованный RTP| M2

Сервер мессенджера (backend) не участвует в DTLS handshake и не знает ключей SRTP. SDP и ICE передаются через него, но медиа идут напрямую peer-to-peer (или через TURN-реле при симметричном NAT).

6. Модель угроз

УгрозаЗащита
Перехват аудио/видео SRTP — медиа шифруются; без ключей DTLS прослушать невозможно
Перехват сигнализации (SDP, ICE) WSS/HTTPS — TLS шифрует весь трафик к серверу
Man-in-the-Middle на медиа DTLS обеспечивает аутентификацию peer’ов (сертификаты); подмена требует компрометации TLS/DTLS
Утечка ключей на сервере Сервер не хранит и не получает ключи SRTP — они только у участников звонка
TURN-сервер видит трафик При использовании TURN трафик идёт зашифрованный (SRTP). TURN ретранслирует зашифрованные пакеты, не расшифровывая их

7. Конфигурация

Для корректной работы и безопасности звонков важно:

  • HTTPS и WSS — приложение должно работать по HTTPS; WebSocket — по WSS
  • STUN — для обхода NAT (например, stun:stun.l.google.com:19302)
  • TURN (опционально) — при симметричном NAT; TURN-сервер должен поддерживать TLS
  • SIP (опционально) — при использовании SIP звонки идут по WSS (SIP over WebSocket)

Параметры задаются в config/config.php (SIP_WS_URL, SIP_STUN_URL, SIP_TURN_*). Подробнее см. CALLS_SETTINGS_AND_STORAGE.md.
